# Provider / Models 使用意图、问题处理与紧凑展示方案

状态：已实施（2026-09-12）。§8 五步全部落地：`/api/meta` protocolVersion=2 + capabilities、inventory schemaVersion=2 必填校验（前端不再回退旧告警逻辑）、static-web dist 指纹防混用、`model-attention.ts` 统一问题列表 + `attention-decisions.json` 持久化忽略、`ModelAttentionPanel` 三页共用、Providers 互斥筛选 tab 与插件默认折叠。验收：`bun run check` / `bun run acceptance` / `bun run test:e2e`（38 项，含「不再提醒跨页面和刷新有效」）全绿；真实常驻实例只读核对——后端 protocolVersion=2、静态资产与 dist 一致、`pickerSource=gateway`、46 个 IM 可见选项、需处理 0、已忽略 0。相关约定已并入 AGENTS.md「问题处理与用户决定（2026-09-12 起）」。

## 1. 目标与范围

用户管理自己想用的 Provider 和模型，不负责修复 OpenClaw 所有能发现的插件目录。

本轮只制定方案，不修改业务代码、不构建、不重启服务、不写真实 OpenClaw 配置，也不提交。保留上一轮未提交改动，实施时逐项复用或修正。

本方案解决：

1. 未启用 / 已确认不用的对象不断进入“不可用与待处理”。
2. Providers → Models → Providers 循环跳转，无法结束问题。
3. “保留”没有持久化意图；刷新后提示仍在。
4. 停用插件切换的效果远离按钮，缺乏反馈。
5. 已启用插件的大卡片和默认展开表格占用过多空间。
6. 新前端与旧后端混用，以及验证结果未覆盖真实常驻实例。

假设：优先管理当前配置的默认 Agent；有独立 Agent 策略时明确标注范围并提供依赖信息，不自动修改其他 Agent。停用和忽略均保留 API Key。不对就说。

这不是用户刷新缓存就能解决的问题：旧后端不因 Web 构建而重新加载代码，但 `static-web.ts` 按请求读取 dist。上一轮构建已改变实际服务的前端，却没有同时更新常驻后端。此前新代码/隔离实例验证不能代表该运行实例已正确。

代码证据：

- `ProvidersView.tsx` 的 `needsAttention ?? (availability !== "available" || unavailableModelCount > 0)` 在字段缺失时恢复旧告警逻辑；Models 页有同类回退。
- Providers 的“前往模型处理”只切路由；Models 的“前往 Providers”也只切路由，不携带对象、不定位动作。
- Models 弹窗“保留”只调用 `closeAction`，不保存用户决定；没有“不再提醒”的实现。
- `PluginProviderGroup` 只要插件 enabled 就展开整个 Provider 表；同名配置 Provider 还可能在上方配置表重复展示。

只读浏览器实测“未启用插件”：展开显示 27 个插件组（21 个停用开关），收起后 6 个插件组（0 个停用开关）。变化的插件区在约 y=1599px，scrollY 始终为 0，首屏长告警不变。因此不能把该按钮判为底层完全无效，但其交互反馈确实无效，且没有影响用户以为会被隐藏的告警区。

这些数值只描述本次本机观测，不硬编码为未来验收期待。截图所属实例若另有不同，需要对该实例补做同样的版本核对。

## 3. 核心规则：不可用是事实，待处理是需要用户行动的事项

保持已有策略、插件状态和可用性事实。增加的是明确的用户决定与统一的问题列表，不再由两个页面自行把 `unavailable` 转换为待办。

“当前使用”依据：主模型 / fallback / image、pdf、utility 等真实依赖、当前有效选择策略和选项，以及明确启用意图。仅有 `.env` 密钥、manifest、闲置 metadata 不算当前使用。开放 policy 下不能把完整 catalog 的所有模型当成用户选用。插件启用但其 Provider 全部被 oc-switch 可逆关闭（选择规则已移出、零 IM 选项）也不算当前使用，归入“已停用”筛选；此时组头同时展示「插件已启用」与「Provider 已关闭」两个维度，Provider 行状态列显示「已关闭」而非运行可用性。

| 情况 | 默认列表与提醒 | 可提供的动作 |
| --- | --- | --- |
| 从未启用的内置插件、没有实际引用 | 只在“已停用”筛选中显示一行，不生成模型待办 | 启用并配置 |
| 已停用且不再出现在 IM，保留了 metadata/Key | 正常停用状态；无警告、无待办 | 恢复使用、清理可选配置 |
| 用户确认暂时不用，尚未停用 | 先提供真实停用；也可仅忽略该问题 | 停用并保留配置 / 本问题不再提醒 |
| 仍在 IM 的停用对象或残留规则 | 每插件/Provider 一条“仍有模型选项”，不逐模型刷屏 | 整组移出选项；可忽略该提示但明确 IM 不改变 |
| 当前选用 Provider 缺 Key / 连接配置 | 每个根因一条，例如“Provider X 缺少认证，影响 7 个选项” | 原地配置 / 不再使用 |
| 一个 Provider 的某个选用模型失效 | 模型级问题，与插件启停分开 | 换模型 / 停用该选择规则 |
| 未选用的目录或 metadata 不完整 | 管理详情中中性展示；不进全局待办 | 补全 / 保留 / 清理 |
| 主模型、fallback 或其他实际依赖异常 | 明确且不可长期忽略的必要行动项 | 显示具体依赖并提供替换/修复 |
| Gateway 探测整体失败 | 一条“无法确认运行状态”，显示上次观测时间 | 重试 / 查看诊断；不制造数十个模型未知待办 |
| 语法/schema 错误导致 OpenClaw 无法加载 | 保留真实阻断项，即使涉及闲置配置 | 修复 / 备份后清理；忽略不能把阻断伪装为正常 |

同一根因只能产生一条问题。例如停用 anthropic 后没有真实依赖时，7 个目录模型不是 7 个问题。一个模型属于多个有效来源时，停用其中一个插件不应自动否定仍在工作的其他来源。

## 4. 用户动作：结束状态必须清楚

去掉含糊的“保留”按钮，按作用分别命名：

| 动作 | OpenClaw 配置 | oc-switch 提醒 | 后续 |
| --- | --- | --- | --- |
| 暂不处理 | 不变 | 保持 | 只是关闭面板，不承诺消除提醒 |
| 本问题不再提醒 | 不变，IM 也不变 | 持久化忽略这一问题 | “已忽略”中可恢复提醒 |
| 不再使用 | 预览后真实停用插件/移出目标选择规则 | 记录停用意图；确认生效后问题解决 | Key 与配置默认保留，可恢复使用 |
| 配置并启用 | 原地填写缺少字段、确认影响后启用 | 新探测确认后问题解决 | 字段完整不代表网络一定可用 |
| 清理保留配置 | 预览并备份后按选项删除 | 根据剩余事实重新计算 | API Key 不在该清理动作范围内 |

默认推荐“不再使用 → 保留配置和 Key”。清理是可选后续，不作为消除停用提醒的前提。忽略只改变提示，不能显示成“已从 IM 移除”。

### 持久化规则

- 只忽略用户明确选择的问题或整个插件/Provider；不支持自动忽略所有 unknown。
- 复用现有 JSON 状态存储、权限和锁机制；不把 oc-switch 管理意图写进 OpenClaw 未定义的配置键。
- 使用当前配置路径、Agent 范围、对象类型/ID、问题 kind 标识记录；只保存非敏感字段。
- 忽略后刷新页面、重启服务、切页面仍有效；换配置路径不继承。
- 同一停用对象仅更新 manifest、版本或新增未使用模型，不重新骚扰用户。
- 用户重新启用、外部配置重新显式引用该对象，或升级为实际依赖/全局加载阻断时重新评估，必要提醒恢复。问题恢复为健康后再发生，应视为新的事件。
- 忽略对象重新打开详情时仍可查看实际状态，不覆盖底层运行事实。

## 5. 处理入口：一个问题，一个可完成的面板

Providers、Models、仪表盘消费同一份 Core 问题列表，统计同一组稳定 issue ID。Providers 页只展示短摘要，例如“2 项需要处理”，不再列满屏 31 个 Provider。Models 页也不复制一整份插件问题表。

点击摘要或行内“处理”，打开共享处理面板，按根因直接提供动作：

- 插件未使用：不再使用 / 本问题不再提醒 / 启用并配置。
- Provider 缺认证：直接呈现已有 Key 编辑组件，敏感内容始终遮蔽；同面板提供不再使用。
- 模型精确规则残留：移出该规则，metadata 清理独立选择。
- 主模型/fallback：先显示具体依赖和可执行的替换动作。无法在本期编辑的依赖提供准确路径与阻断理由，不提供空转的“处理”。
- 插件多 Provider：一次展示完整影响范围，不要求逐模型确认。

复用现有对话框/表单；暂时必须去其他页时，应携带对象 ID，自动选中目标并打开对应操作，完成后同步原问题状态。禁止无上下文的双向跳转。

写入成功但 Gateway 未确认时，显示“一项变更待应用/核验”；不说停用失败，也不恢复几十条子模型告警。Core 确认 IM 不再含目标后问题解决；确认期间可保留上次观测，不猜结果。

## 6. Providers 布局建议

比较两种合理方案：

| 方案 | 优点 | 成本 |
| --- | --- | --- |
| **紧凑表格 + 行展开（推荐）** | 同屏可看多插件、现有 DataTable 可复用、手机自然退化 | 展开后仍纵向浏览，但范围可控 |
| 左侧列表 + 右侧详情 | 单个 Provider 编辑空间充分 | 导航/选中态、手机详情、同名多来源需要更多设计 |

本期采用第一种；将来信息量明显增长后再评估左右分栏。避免用双列大卡片缩小宽度却仍保留所有展开内容。

### 页面结构

```text
Providers                 搜索…                 添加 Provider
当前配置 · 默认 Agent · Gateway 已确认/上次观测时间
[当前使用] [已停用 21] [全部配置]           [需处理 2] [已忽略 3]

对象                 状态        IM 选项     问题       操作
▸ Google（插件）     已启用        10          —         …
▸ NVIDIA（插件）     已启用        13          —         …
▸ 自定义代理         使用中         8          1         …
```

- 当前使用 / 已停用 / 全部配置是互斥范围，不再同时组合两个含糊的开关。
- “已停用 21”的数量与实际结果一致；搜索后显示“匹配 x / 总计 21”。来源有歧义时显示未确认，不套入停用计数。
- 切换筛选原位替换表格、回到结果顶部，保留键盘焦点与选中反馈；不在远处追加内容。
- 所有插件默认折叠，一插件一行；展开才显示所贡献的 Provider。子 Provider 的模型目录再次按需展开。
- 原始状态/来源 badge 精简至主行一个使用状态及必要问题标记，细节进入展开区。
- 同名 config + plugin Provider 作为同一个 Provider 的多来源详情，不再重复独立大卡片。一个 Provider 有多个插件所有者时，详情列出关联，禁用影响由 Core 计算。
- 插件可能服务工具/语音而不提供当前聊天选项。插件仍应在管理范围可找到，标注“仅非模型能力”，不能因 IM 选项为 0 被误认为未启用。
- 手机保留名称、状态、问题与操作；子表信息纵向展示。桌面先验证 1280px、手机 390px，body 不横向溢出。

验收密度目标：1280×800 下默认折叠状态至少看到 8 行对象，不被空白、嵌套卡片和长告警占满首屏。

## 7. 数据契约、加载和实际运行版本

### 先解决版本混用

- 增加服务身份/协议能力信息：前端资源版本、后端启动版本、inventory schema 版本与必要 capability。
- 新版核心字段成为该 schema 下的必填；不能用 `?? availability` 把未知协议解释成旧业务规则。
- 新前端遇旧协议仅提示一次“服务需更新/重启”，保留可安全读取的基础信息；依赖新状态的诊断/写操作不按猜测执行。
- 后端启动时绑定对应静态资源版本。支持原子替换后同时验证，或发现 dist 与启动版本不匹配时明确提示；不能悄悄混用。
- 最终验证必须连接用户实际常驻实例，检查进程启动版本、页面 asset、API schema、浏览器请求目标一致。重启/部署属于实施交付阶段，本讨论不执行。

### 统一问题与动作

- Core 继续负责事实合并；集中生成问题（kind、owner、severity、affected refs、resolution actions、blocked reason），前端不自行重新分类。
- 一个 `issueId` 可从不同页面打开同一处理器；全局数量按 issue 去重，不累加 Provider 数与模型数。
- 已忽略记录不计入待处理；必要依赖和加载阻断优先于忽略。未知探测仅作为一条数据状态，不污染每行处理逻辑。
- 保留现有写入事务、自动备份、Key 边界及 fresh preflight；不为 UI 改动重写底层配置管理。

### 性能

- 沿用上一轮异步并行、同 scope 请求合并和文件版本失效。
- 页面切换筛选/折叠不重新 shell-out；一次已确认 snapshot 供多个页面复用。
- 先展示紧凑基础行；子 Provider、模型表按展开渲染。大型完整 catalog 仅显式浏览才请求，不阻塞当前使用列表。
- 保留上次成功结果和时间；刷新局部显示状态。scope 改变必须隔离缓存，不能展示另一配置的旧结果。
- 验收：缓存筛选/折叠反馈在 100ms 量级；冷启动整页以本机当前条件 ≤3.5 秒为目标，同时记录命令耗时以区分 CLI 与 UI 延迟。

## 8. 建议实施顺序

1. **协议与运行一致性**：复现新前端/旧后端；去掉危险回退，补能力检查和实际服务验收。先给当前症状正确解释。
2. **问题状态与用户决定**：统一 issue 计算和持久化忽略；先覆盖 inactive、实际依赖和刷新/重启不复发。
3. **原地处理**：复用表单与事务，打通不再使用/修复/忽略/恢复提醒，结束循环跳转。
4. **紧凑 Providers 展示**：互斥范围、默认折叠、同名多来源归并、搜索与数量一致。
5. **集成验收**：前后端同版服务、Gateway 离线/在线、两种屏幕、保存决定后重开应用。确认目标实例后再进行实际更新。

主要涉及：`model-inventory.ts` 与新问题/决定模块、`json-state-store.ts` 现有能力、Server context/只读 DTO/动作端点、`ProvidersView` / `ModelsView` / `PluginProviderGroup` / 共享处理面板、静态资源服务与 launcher 验证。

不引入数据库、新 shared contracts 包或新的 UI 框架。完整的逐文件实现计划在本方案确认后编写。

## 9. 验收场景

| 场景 | 必须看到的结果 |
| --- | --- |
| 新前端连接旧后端 | 一条协议不兼容提示；不恢复 76+10 项假待办；受影响写操作不能误执行 |
| anthropic 未启用且无引用 | 两页都无 anthropic 待办；“已停用”里只有一行，不要求逐模型处理 |
| 已启用、缺 Key，但用户确认不用 | 原地停用/忽略成功；刷新和重启后同一问题不再出现 |
| 忽略但未停用 | 文案明确 IM 不变，仍可在已忽略列表恢复提醒 |
| 用户重新启用 / 加入实际依赖 | 重新校验，缺配置时恢复必要提醒，不沿用陈旧忽略 |
| 插件保留 metadata，但没有 IM 选项 | 无待办；清理始终可选 |
| 插件已停用但 exact 规则残留 | 一条整组残留提示，原地处理后关闭，Key 不变 |
| primary/fallback 或独立 Agent 使用目标 | 明确具体依赖，不允许用忽略假装恢复健康 |
| 全部 CLI/Gateway 探测失败 | 一条探测提示，保留带时间的旧结果；无逐模型批量假错误 |
| 已停用筛选 21 项 | 原位显示 21 行；切回当前使用立即恢复，搜索/结果数吻合 |
| 20 个已启用插件、各多个 Provider | 默认都是紧凑折叠行，仅展开目标子表；手机无横向页面溢出 |
| 新代码与用户常驻实例 | 后端协议、进程版本、前端资产、请求目标一致，不能只凭隔离测试报告完成 |

验证入口复用 `bun run check`、`bun run acceptance`、`bun run test:e2e`，增加上述行为用例，而非只锁定固定数量或文案。业务实现前写能复现问题的测试。当前本轮仅验证现状、撰写方案。

## 10. 待讨论的两个产品取舍

1. 推荐采用“紧凑表格 + 行展开”，本期不做左右详情分栏。
2. 推荐把“不再使用（真实停用）”作为主动作，“本问题不再提醒（不改 IM）”作为次动作。未启用且无依赖的内置插件自动安静，无需逐项忽略；主模型等关键依赖不能永久忽略。
